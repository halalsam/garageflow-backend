# GarageFlow Backend — Architecture & Contributor Guide

A practical map of how this backend is put together and **how to add or change a
service**. This file is the *how* (patterns); [`REQUIREMENTS.md`](./REQUIREMENTS.md)
is the *what* (GarageFlow scope, schema, endpoints) — read it first when building
out the API. For setup/run instructions see `README.md` (create in Milestone 0).

> GarageFlow is India-first — ₹ (paise in the DB), GST, Indian plates, roles
> tech/manager/admin. The currency/date/enum examples below reflect that;
> REQUIREMENTS.md is authoritative for scope.

---

## 1. The one rule that governs everything

> **`../garageflow/types/api.ts` is the contract. The API must emit those exact
> shapes.** (That file is extracted from `../garageflow/data/mock.ts` during the
> mobile cutover — see REQUIREMENTS §11. Until then, `data/mock.ts` *is* the
> contract.) The DB schema is free to differ; the gap is closed in one place —
> the serializers.

```
Postgres row  ──Prisma──▶  entity (UPPER_SNAKE enums, paise, DateTime)
                               │
                     src/common/serializers.ts   ◀── the boundary
                               │
                               ▼
   JSON the app expects  (₹ as numbers, "26 Jun 2026", status → label + tone)
```

Three helper layers back the serializers:

| File | Responsibility |
| --- | --- |
| `src/common/serializers.ts` | row → contract JSON. **Every response goes through here.** |
| `src/common/enum-maps.ts` | `*ToApi` (serialize) and `apiTo*` (DTO input) enum maps |
| `src/common/format.ts` | `toRupees`/`toPaise`, Indian date strings (`formatDate`, `formatTime`, `relativeTime`, `monthLabel`), `initialsOf` |

If a response field is wrong, the fix is almost always in `serializers.ts`. If a
DB enum/money mapping is missing, it's in `enum-maps.ts` / `format.ts`.

## 2. Request lifecycle

```
HTTP → [global JwtAuthGuard]      (bypassed by @Public())
     → [global RolesGuard]        (enforces @Roles(...))
     → [ValidationPipe]           (DTO validation; whitelist + transform)
     → Controller                 (thin: routing + @Body/@Query/@Param)
     → Service                    (business logic + Prisma)
     → serializer                 (row → contract shape)
     ← [AllExceptionsFilter]      (errors → { statusCode, message, errors? })
```

- **Global prefix** `/api` (set in `main.ts`). Static `/uploads` is *not* prefixed.
- **Auth is global**: a route needs a valid Bearer access token unless annotated
  `@Public()`. Get the caller with `@CurrentUser()` (`AuthUser = { id, email, role }`).
- **Validation pipe** strips unknown fields (`whitelist`) and coerces types
  (`transform` + implicit conversion). Its `exceptionFactory` builds the
  field-grouped `errors` map.

## 3. Anatomy of a module

Every feature module is the same shape (see `inventory/` for a complete example):

```
src/<feature>/
  <feature>.module.ts       declares controller + service
  <feature>.controller.ts   routes only — delegates to the service
  <feature>.service.ts      Prisma queries + serialize(...)
  dto/                       *.dto.ts with class-validator decorators
```

`PrismaService` and `StorageService` are **global** (no import needed). Register
the module in `app.module.ts`'s `imports`. If a service is reused by another
module, `export` it (e.g. `VehiclesModule`, `CustomersModule`).

## 4. Conventions (do these every time)

- **Money**: ₹. DTOs accept **rupees**; convert with `toPaise()` on the way in.
  Serializers emit a **number of rupees** via `toRupees()` (the app formats it
  with its own `inr()`). DB columns are `Int` **paise**. All current data is
  whole-rupee. **GST** is derived from `gstRate` (round to whole rupees; CGST =
  `round(gst/2)`, SGST = `gst − cgst`). Invoice paid/balance/status are derived
  from payments — never stored (see REQUIREMENTS §5).
- **Enums**: never emit a raw Prisma enum. Map with `enum-maps.ts`
  (`jobStatusToApi[...]` out, `apiToJobStatus[...]` in). When you add an enum
  value, add it to **both** maps. `JobStatus` serializes to **both** a `status`
  label and a `tone` (IN_PROGRESS→`IN PROGRESS`/blue, AWAITING_PART→amber,
  REVIEW→purple, COMPLETED→green); `UserRole` also emits `roleLabel`+`roleIcon`.
- **Dates**: emit the Indian display strings the app expects — `formatDate`
  (`"26 Jun 2026"`), `formatTime` (`"8:30 AM"`), `relativeTime` (`"12m ago"`),
  `monthLabel` (`"June 2026"`). Where the app also needs the raw ISO
  (`Invoice.issuedAt`, `Payment.at`, ledger `at`), emit it alongside the display
  string. Fixed historical dates are formatted in **UTC** for determinism.
- **IDs** are UUID strings generated by the DB. Never hard-code IDs; wire
  relations by reference (see `seed.ts`).
- **Errors**: throw Nest `HttpException`s (`NotFoundException`, `ConflictException`,
  …). The filter shapes them. For field errors, throw
  `new ConflictException({ message, errors: { field: [msg] } })`.
- **Lists**: return a bare array when the app expects `T[]`; use
  `paginate(rows, total, page, pageSize)` only where the contract is `Paginated<T>`
  (currently just `GET /customers`).
- **Reuse the include shapes** `jobCardInclude` / `customerInclude` from
  `serializers.ts` so query results match the serializer's payload type.

## 5. Recipe: add a new endpoint to an existing service

1. **DTO** — add/extend a class in `dto/` with `class-validator` decorators
   (money fields documented as rupees).
2. **Service method** — query via `this.prisma`, map money/enums, `return
   serializeX(row)`.
3. **Controller method** — add the route; keep it a one-liner that calls the
   service. Add `@ApiBearerAuth()` if the controller isn't already annotated.
4. **Verify** — `npm run build`, then `curl` it (see README smoke-test patterns)
   and confirm the JSON matches the mobile type.

## 6. Recipe: add a whole new module

```bash
# create src/<feature>/{<feature>.module.ts,.controller.ts,.service.ts,dto/}
```
- Model it on `inventory/`.
- Add a `serializeX` to `serializers.ts` (and include-shape if it has relations).
- Register the module in `app.module.ts`.
- Keep the route in sync with the contract in [`REQUIREMENTS.md`](./REQUIREMENTS.md) §7
  and the mobile `types/api.ts`.

## 7. Recipe: add a field to an entity

1. Edit `prisma/schema.prisma`.
2. `npm run prisma:migrate` (names + applies a migration, regenerates the client).
3. **Restart the TS server** in your editor so it sees the new client types
   (VS Code: “TypeScript: Restart TS Server”). The CLI (`npm run build`) sees
   them immediately — editor squiggles after `prisma generate` are almost always
   a stale TS server, not a real error.
4. Surface the field in the DTO (input) and `serializers.ts` (output); update
   `seed.ts` if needed.

## 8. Prisma workflow

| Action | Command |
| --- | --- |
| Change schema → migration + client | `npm run prisma:migrate` |
| Regenerate client only | `npm run prisma:generate` |
| Re-seed (clears + recreates) | `npm run prisma:seed` |
| Nuke & rebuild DB | `npm run db:reset` |

`seed.ts` is re-runnable (it clears tables in FK order first) and is the place to
keep demo data realistic.

## 9. Gotchas

- **Stale TS server after `prisma generate`** — see §7.3. Trust `npm run build`.
- **`dist/main.js` location** — `tsconfig.build.json` pins `rootDir: src` and
  excludes `prisma/`, so output is `dist/main.js` (not `dist/src/main.js`). Don't
  remove those or the start script breaks.
- **Multipart routes** (`POST /job-cards`, `POST /bookings`) use file
  interceptors; text fields still validate through the DTO. Files arrive on a
  separate `@UploadedFiles()` param, not in the DTO.
- **`PATCH /job-cards/:id` returns `{ message }`** by contract (the client types
  it that way) — don't "fix" it to return the `JobCard`.
- **DB host port**: pick a free one in `docker-compose.yml` + `DATABASE_URL`
  (5432 is often already in use locally — just keep the two in sync).
